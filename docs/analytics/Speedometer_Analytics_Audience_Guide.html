1. How it fits together

The app sends events (things that happened, e.g. a purchase failed) and sets user properties (the user's current state, e.g. premium or free). An audience is a saved rule over those, e.g. free users whose last purchase failed. Audiences fill only after you create them (allow 24 to 48 hours). No Firebase console changes have been made; the labels below describe the usual GA4 screens and were not checked against a live property. Tick the boxes as you go (saved in this browser only).

First-time vs returning. A first-time user is in their first app launch; from the next launch on they are a returning user. Users who already had the app before analytics was added start as returning. The app sets the user property user_cohort (first_time or returning) and also puts it on every event, so an event keeps the cohort the user had when it happened. Every audience below is built for one of the two, grouped by the app's features and flows, so you can see where new users get stuck separately from where established users do.

2. Check the events arrive (DebugView)

  1. Build a debug app that sends events (debug builds only log to Logcat by default): gradlew.bat :app:assembleDebug -PanalyticsDebugEnabled=true
  2. On a test device or emulator: 
    adb shell setprop debug.firebase.analytics.app com.speedometer.app
  3. Firebase console, Analytics → DebugView. Use the app twice: a fresh install (first-time) and a second launch (returning).
  4. Confirm the events in section 7 appear, that user_cohort is first_time on the first launch and returning after, and that no personal data (search text, file paths, purchase tokens) is present.
  5. Turn it off: 
    adb shell setprop debug.firebase.analytics.app .none.

8. What the events cannot tell you

  • Events show what users did and which technical failures happened; they cannot prove WHY someone left or uninstalled.
  • A first-time user stays first-time until they save their first trip. Someone who reinstalls is counted as first-time again, because the counters live on the phone.
  • People who already had the app before analytics was added start as returning (they finished onboarding before).
  • No location, route or personal data is ever sent. Trip length is only sent as a bucket (under_1m, 1_to_5m, 5_to_30m, over_30m).
  • Debug builds print events in Logcat and send nothing; only release-style builds send events, and only when google-services.json is in the app.
  • Audiences are prospective: they fill after they are created, allow 24 to 48 hours.
  • Audiences are prospective: they fill after creation, not from past data.
  • User properties show the last value the app set; a user who has not opened the app since an update keeps their old values.
  • Respect user consent: events follow the app's Firebase consent configuration.
